## Every step

- **The lane = the `premiere-pro` skill driving the pinned `vendor/premiere-mcp/` engine (v1.2.3) through the CEP bridge panel**, or headless via `lanes/premiere/premiere-bridge.mjs` (`replay` / `zoom` / `frame` / `grade-layer`, no MCP session needed). Graphics on the timeline validated 2026-07-18; AME banned (exportAsMediaDirect via ES if a bounce is truly needed); `zoom` takes `at` (sequence time) or `offset` (frames) and clears only from the ramp start. Read-back-after-write, always. Wiring and pin: the skill.
- **The bridge has ONE output contract: one line out, `ERROR:` in, a 65535-char return cap, and a timeout you pass (2026-09-19).** `node lanes/premiere/premiere-bridge.mjs es (--job projects/<job> | --no-guard) '<script>'` is the sanctioned runner for ad-hoc ExtendScript and owns all four; `lanes/premiere/pes.py` is the Python side of it (`es(script, timeout=None, job=None)` — pass `job` to run the guard on THAT call — plus `paged(make_script, size=40)` for a readback that would hit the cap), and a lane script imports it rather than growing its own parser. It wraps the caller's script in a try/catch, so a runtime failure comes back as `ERROR: <message> @ line <n>` instead of the bare "ExtendScript execution failed via CEP evalScript()" that costs two dead round-trips to localize. It prints EXACTLY one line — the result verbatim, or single-line JSON for an object; that `ERROR:` line comes back on STDOUT with a non-zero exit (only a transport failure and the cap refusal go to stderr), so a caller keys off the exit code, never on stderr being empty — and otherwise parses stdout with a plain `json.loads` instead of guessing at interleaved `[INFO]` lines. It refuses, naming the cap, rather than printing a result that hit CEP's return limit: a readback over that size is PAGED, a fixed batch of rows per call, because full media paths make a whole-track read blow through 64 KB and surface as `Unterminated string … char 65534` inside the caller's parser. And `--timeout <ms>` reaches both the panel watchdog and the server's wait, which is what a long `exportAsMediaDirect` needs — the 45 s default is a watchdog, not a transport limit, and without it a perfectly good multi-GB export reports failure. **`es` is a WRITE path (the scripted export runs through it), so it runs the active-project guard like `replay` / `zoom` / `grade-layer` / `lay`, and `--no-guard` is the deliberate opt-out for a read that is not about a job** — ONE of the two is required and the command exits 2 without either, so the guard cannot be skipped by forgetting it exists (an unguarded ad-hoc script is exactly how 37 graphics landed on the wrong open project). `pes.es` passes `--no-guard` per call because a lane script guards ONCE at startup through `job_guard.require_job_project`.
- **The panel refuses a script whose TEXT holds `process.`, `eval(`, `require(`, `new Function(`, `__dirname`, `__filename` or `child_process`, string literals included, as a bare "Script validation failed" (audit, 2026-10-13).** The pinned panel's `validateScript` (unchanged upstream through v1.2.9) matched a clip named `Editing Process.MP4` or `Medieval (Live).wav` inside the replay's own name list, so every command that named it failed with no cause given. Every name or path the bridge writes into a script goes through `bridge-lib.mjs` `esLit` (`pes.py` `es_lit` from Python): JSON with each `.`, `(` and `_` inside a string as a `\u` escape, which ExtendScript reads back unchanged; the bridge names the cause when the panel refuses anyway. `replay` and `zoom` also exit 2 with nothing saved on an `ERROR` (both printed it, saved and exited 0), and `replay` finds every segment's clip before it lays the first. Regression: `workflows/test_premiere_bridge.py` D25/D32/D33, `test_place_music.py`.

Launch = `./lanes/premiere/premiere-up.sh [project]` with the CEP autostart patch applied by `apply-autostart-patch.py` (re-run after any engine re-clone).
- **Never escalate a stuck quit to `kill` / `kill -9`.** Premiere logs any non-graceful exit as a CRASH: the next launch opens on an error-report modal that blocks the CEP panel, so bridge autostart silently fails, and post-kill timeline state comes back subtly wrong even after a `save_project` that returned success. Save through the bridge, quit gracefully (ExtendScript `app.quit()`, not an AppleEvent), then wait on the pid — and if it still will not quit, STOP and hand the app back to be quit by hand. `premiere-up.sh --restart` already refuses to escalate and exits with that instruction; keep it that way.
- **An ExtendScript edit does not dirty the project (Windows 26.5.1, 2026-09-27).** A marker made by script left no `*` in the title, and a quit (the bridge's `app.quit()` or a window close) raised no save dialog and dropped it; a QE edit (a razor) does dirty it and raises "Save changes to '<name>.prproj' before closing?". So every lane write saves itself, and a quit is never the save. On Windows `premiere-dismiss.sh` answers that dialog: Escape = Cancel (Premiere stays up), Return = Save, `--key 2` = D = Don't Save (proven 2026-10-13: the dirty project closed and its file kept its pre-edit clips; the dialog's buttons are Adobe controls, not Win32 buttons, so a key is the only way to a button).

An invisible native alert is diagnosed with `sample <pid>` (`UI_MessageBox::RunModal`) and dismissed with `lanes/premiere/premiere-dismiss.sh`; never kill Premiere for it.

Keep a byte copy beside every write; when a write is refused, diff Premiere's OWN save of the same edit on the same base against the tool's write (you make the edit by hand once) instead of opening more test copies; open only a write that diff has explained, at most one per hypothesis, after telling you a modal may appear.

- **Converting a placed 1080 sequence to 4K is one ES pass (2026-09-07, your-job):** `seq.setSettings()` with videoFrameWidth/Height 3840/2160 takes effect on a populated timeline; every already-placed clip keeps Motion Scale 100 = its native pixels, so set 200 on the 1080 footage, the placeholder AND the GRADE adjustment layer (its Motion scales the layer's BOUNDS, which is exactly the coverage needed — verify by toggling the layer and reading the corners), 100 on true-4K sources (100.1 on a 3836-wide capture). - **A timeline change is bracketed OFFLINE from the auto-saves (2026-09-10, your-job).** A `.prproj` is gzip XML; `<Start>`/`<End>` ticks ÷ 8,475,667,200 = frames at 29.97 (254016000000 ticks/s × 1001/30000), so diffing those values between two auto-saves says WHEN a cut moved without opening anything. A 10-frame drag of a V1 clip (source in/out unchanged, the previous clip's tail overwritten, a 10-frame hole left behind) landed between two auto-saves while the only commands running were file reads, i.e. from the Premiere UI; the next placer save then persisted it, because `--verify` reads the graphics rows only, never V1. The repair primitives: `trackItem.move(seconds)` is a RELATIVE shift (the vendor passes a plain number) — **and on script-laid clips the linked A1 clip did NOT follow it (astra final-thoughts, 2026-09-14: 20 V1 clips closed a ripple gap, their 20 A1 clips stayed 4.96 s late until moved separately), so move the audio track's items by the same delta and read V1/A1 start, end and inPoint back PAIRWISE before saving;** `clip.end = t` extends a clip (speed stays 1) but the DOM's `outPoint` reads STALE afterwards, so the proof is a voice-only bounce over in/out (`exportAsMediaDirect(wav, Wave48mono24.epr, 1)`) cross-correlated against the raw source, never the readback — **and the stale value outlives the session that caused it: a LATER read of that timeline sees an `outPoint` shorter than the clip and it looks exactly like a hand trim (your-job, 2026-09-21: an in-place +21-frame extend from the day before was logged as the creator cutting a line back out, a wrong EDL was written from it, and the re-derived transcript ran 0.876 s early for everything after that clip, mis-syncing six graphics; the program still played the full range, NCC 0.998 against the raw). When an EDL is derived from a live V1 readback, source-out is `inPoint + (end − start)`, never `outPoint`; any clip where the two disagree by more than a frame is reported as STALE-OUTPOINT, not as an edit, and the derived EDL's total must equal the sequence's length** (`lanes/premiere/live-edl.py` is that reader: it prints STALE-OUTPOINT, checks the total, refuses V1 media no EDL names, and writes only with `--write`, backup first; `--edl` points it at another sequence's EDL; `premiere-bridge.mjs diff-edl` derives the out the same way; proven live 2026-09-23, where the stale outPoint also read LONG after an in-place trim and survived save, close and reopen); `seq.clearInPoint` does not exist, `setInPoint(-400000)` restores the unset state.
- **ExtendScript mutations do NOT enter Premiere's undo stack (your-job, 2026-09-19).** Five `app.executeCommand` undos and the MCP `undo` / `multiple_undo` tools all returned success and changed nothing after a scripted wipe, so there is no recovery inside the app: the SAVED `.prproj` is the only rollback. `save_project` BEFORE any write that touches clips which already exist (a re-lay, a sweep, a remove, a ripple), and count the affected track's clips before and after.
- **`clip.disabled = true` is how a clip is muted from a script.** `TrackItem.setDisabled`, QE's `setEnabled` and the vendor `batch_enable_disable` tool all fail or act on the wrong set (it reported changing 596 clips); read the flag back as `clip.disabled`.
- **Two sequences are proven identical with `uv run lanes/premiere/timeline-dump.py projects/<job> --diff "<organic>" "<AD>" --until <CTA s>`, never a hand dump (2026-09-23).** A one-shot dump of a graded sequence hits the CEP return cap (350840 chars: the Lumetri blob), and a hand pipeline swallowed that error into an empty `dump.json`. The tool reads both sequences by name without activating them (either may be active, no `VE_SEQUENCE`), pages 40 clips then 40 transitions per call, hashes every component property inside Premiere, and under `--until` hashes the keyframes only as they play before the CTA, so a bed fade that moved with the AD's end is not a difference. It prints only what differs (exit 1); a refused or failed read is exit 2, never 1. Proven live, your-job's own organic and AD included (about 11 s a run). It compares media PATHS, so an AD that carries its own pixel-identical caption render never reads IDENTICAL: that one stays a pixel proof.
- **timeline-dump.py quantizes only NON-INTEGER numbers, and walks arrays by hand (2026-09-23).** A script-copied Level key came back one float32 ulp off after save and reopen (proven live), so fractions hash at 5 significant digits. A colour param's getValue() is a 64-bit PACKED integer (White Balance 255,192,192,192 = 18374897589125431000), which 5 digits would collapse to its alpha, so integers hash verbatim. Premiere's ExtendScript JSON.stringify IGNORES a replacer function, so ES code must never rely on one: walk the value first. The node mock in `workflows/test_live_edl.py` ignores replacers too.
- **The project bin is organized before the step-7 handoff: `uv run lanes/premiere/organize-bins.py projects/<job> --apply` (2026-10-04: "Organize the project bin, please"; promoted 2026-10-05).** Every loose root item is sorted by what the TIMELINE uses (project-item nodeIds on every track), never by name: 01 Sequence · 02 Footage · 03 Corner Cam (Camera, Shadow) · 04 Recordings · 05 Graphics (each by section) · 06 Grade · 07 Unused (old camera pieces, old versions, retired renders). Nothing is deleted; the `sfx` bin stays at the root under its own name, because `place-sfx.py` finds it there. A dry run (no `--apply`) prints the moves; it only sorts what is loose at the root.
- **ExtendScript splits an empty string by a regex into `[]`, not `['']` (2026-10-07).** `''.split(/[\/\\]/).pop()` is `undefined`, so a script that names a clip from `getMediaPath()` crashes on any clip with no media behind it (a Premiere Graphic / title the creator laid by hand): the placer's swap died on one with "undefined is not an object". Default it: `.pop() || ""`.

## Step 2 · replay

- **Never render the flat cut on this lane; the audio polish is step 3, right after the replay.** `RENDER=0 splice.sh` → `premiere-bridge.mjs replay` (time-to-timeline is the metric, transcription the only slow step). No gain, no level-matching during the cut. Then `uv run lanes/premiere/audio-polish.py projects/<job> --apply` (measured gain + Hard Limiter −6 dBFS as clip effects on every A1 clip, readback-verified); a re-replay discards clip effects, re-apply before saving. Owner: `premiere-pro` skill § Step 3.
- **OBS recordings carry two identical AAC tracks and Premiere silently refuses the file.** Remux losslessly first (`ffmpeg -i raw.mp4 -map 0:v:0 -map 0:a:0 -c copy -movflags +faststart out.mp4`); duration is unchanged so an EDL still applies. Clip deletion IS scriptable: `moveBin` into a fresh bin, then `deleteBin()`.
- **A frame-range sweep that removes clips must name its TRACKS (your-job, 2026-09-19).** Moving a section to the front of a sequence with a remove-then-shift script swept every track over the vacated range and silently took two SFX with it; the loss only surfaced when the creator noticed a missing whoosh. Sweep only the tracks the move owns, and run `place-sfx.py --diff` then `--verify` afterwards; zero missing, extra or drifting cues is the gate (the step-6 owner is [`presets/youtube/default/sfx.md`](../../presets/youtube/default/sfx.md) § Definition of done).
- **An audio `overwriteClip` from a SUBCLIP ignores the out-point and lays the WHOLE media, wiping every later clip on that track (your-job, 2026-09-19).** The end-trim afterwards hides it: the clip looks right and three later clips are simply gone. Lay audio rows in ASCENDING time order so each lay re-creates the next, read the laid LENGTH back before trimming, and count the track's clips before and after.
- **A laid clip's colour cannot be READ back on this lane, so the confirmation is a window grab (your-job, 2026-09-19).** `TrackItem` exposes no `getColorLabel` and every item-side answer (the MCP's `select_clips_by_color` included) reports the PROJECT ITEM's current label, not the colour the clip displays — which is how an item-name audit "proved" five clean colour runs on a timeline that was visibly wrong, and your-job CAM CUTS shipped 37 grey camera clips. `workflows/window-grab.sh "Adobe Premiere" out.png` grabs the window in place (Retina, so the capture is 2x the point size) and a crop of the V1/A1 strip shows the runs at a glance. The rule the check serves is the owner's: `premiere-pro` § colour labels.
- **A HARD-BOUNDARY subclip is how you lay one audio row safely.** `createSubClip(name, in, out, 1, 0, 1)` lays exactly its own length, so re-laying a single A1 clip no longer wipes the rest of the track (the plain-subclip runaway above); it also carries its own colour label, which is how a mis-coloured clip is fixed in place. Its in-point is SUBCLIP-relative, so any EDL derivation must map it back to source time rather than reading `inPoint`, and a subclip laid over a dialogue row is skipped in an A1 cross-check by name rather than trusted as source time. **Where a lay subclip starts in its media is its metadata, never `getInPoint()` (live, 2026-09-23).** On the subclip `lay` makes, `ProjectItem.getInPoint()` reads 0 (so do `getInPoint(1)` and `getInPoint(4)`) and `getOutPoint()` the subclip-relative length; the start is the `<premierePrivateProjectMetaData:offset>` inside `Column.Intrinsic.VideoInPoint` in `getProjectMetadata()` (it read 508565433600, the lay's 2.0021 s in-point to the tick; SubclipStart shows it as a timecode), and the track clip's `inPoint` counts from that offset. On timecoded media the offset includes the start timecode (next bullet); a Source Monitor mark on a master moves `getInPoint()` and leaves the offset at 0. `live-edl.py` refuses a lay subclip rather than map it.
- **A project item's VideoInPoint offset is on the media's TIMECODE clock, not its media clock (live, 2026-09-23).** On a master it IS the file's start timecode (01:00:10:00 at 23.976 read 86640 frames). On a `lay` subclip it is the start timecode plus the subclip's start. Any tool that maps a lay row onto source time takes the file's start timecode off first (ffprobe `timecode`, `workflows/grey-source.py` probe `tc_frames`, in ticks on the source grid; drop-frame timecode counts SMPTE-DF real frames, proven at 29.97 DF). Only media with no timecode has a master offset of 0. `frame-proof.py` does this, and it reports an offset below the timecode as unmeasured (exit 2), never as a verdict. Its one blind spot: an item re-timecoded in Premiere (Modify > Timecode) to a start AFTER the file's own reads as a subclip start and FAILs correctly placed rows; undo the override before proving.
- **A head trim is `start =` AND an in-point written in TICKS; a float-seconds in-point can render the frame before while every readback says it is right (2026-09-22, proven on program grabs of a grey-coded source).** `clip.start = t` moves the head and leaves the in-point where it was, so the picture slides a frame; the in-point has to be moved by the same delta. Written as `ti.seconds = inPoint.seconds + delta`, it landed ONE TICK under frame 767: Premiere floored it into frame 766, and `.seconds` readbacks, a 0.002 s tolerance and a frame-rounded readback all reported 767. Do the arithmetic on `Number(x.ticks)`, write `ti.ticks`, compare ticks exactly, and prove a trim on a program grab (`lanes/premiere/frame-proof.py --clear-previews`). `premiere-bridge.mjs lay` does this for the clip it straddles, and `place-blur.py` for each blur layer's in-point (V1's mapping summed in ticks, written as `ti.ticks`, the readback compared tick-exact; proven live 2026-09-23); `trackItem.remove(false, false)` on a video-only remnant leaves the linked A1 clip alone. **A `trackItem.inPoint` written in ticks is stored VERBATIM on a mixed-rate clip too:** on 24 fps and 30 fps sources on a 23.976 sequence the saved in-points sit on neither the source nor the sequence grid (your-job's `.prproj` decoded, and program grabs on a grey-coded source, 2026-09-23). Only `overwriteClip` / `setInPoint` floor to the grids; the trackItem setter does not.
- **An alternate camera angle is lip-sync-measured BEFORE its first clip is laid (2026-09-19).** `uv run workflows/lip-sync.py <cam> --audio <mic-source> --mouth-crop <w:h:x:y>` (the crop is measured off one frame of the cam — `rough-cut` § Gotchas; without it the tool exits 2 UNMEASURED rather than answering); on FAIL each camera clip's source in-point slips LATER by its own lag AT ITS OWN SOURCE TIME — the lag drifts across a long take, so one number for the whole angle is wrong — with the clip's timeline start and end unchanged, and the applied lag is stamped into the clip name (`CAM +Nf`) so re-running the pass is idempotent. Prove it on a timeline export, never the readback. Owner: `rough-cut` § Gotchas.
